# Vercel deployment guide (Production + Preview)

This repository is static-first by design (Next.js App Router + committed report artifacts), which keeps Vercel operations simple and predictable.

> Scope reminder: page rendering must not depend on runtime crypto API fetching. External data is generated by batch scripts and committed as static artifacts.

For troubleshooting after go-live, see `docs/operations/vercel-notes.md`.

## 1) Connect GitHub repository to Vercel

1. Sign in to [Vercel](https://vercel.com).
2. Click **Add New... > Project**.
3. Import GitHub repository `castanhf/Weekly-Crypto-Pulse`.
4. Keep/confirm build settings:
   - **Framework Preset**: `Next.js`
   - **Install Command**: `npm ci`
   - **Build Command**: `npm run build`
   - **Output Directory**: default (`.next`)
5. Click **Deploy**.

## 2) Preview deployments for branches and PRs

Vercel creates Preview deployments automatically for pull requests and non-`main` branches.

Configure once:

1. Go to **Project Settings > Git**.
2. Set **Production Branch** = `main`.
3. Leave Vercel Git integration enabled for commit/PR comments and status checks.

Validation flow:

1. Push a branch.
2. Open a PR to `main`.
3. Confirm:
   - a Preview URL is generated,
   - the PR shows Vercel deployment checks,
   - the Preview build passes with no manual steps.

## 3) Production deployment from `main`

1. Merge PR into `main`.
2. Confirm Vercel starts a **Production** deployment for the merge commit.
3. In **Deployments**, open the production deployment and verify:
   - status is **Ready**,
   - correct commit SHA,
   - expected production domain assignment.

## 4) Node version expectations (local + Vercel)

### Local

Node runtime is pinned through `.nvmrc`:

- `.nvmrc` => `20.14.0`

Use locally:

```bash
nvm install 20.14.0
nvm use 20.14.0
node -v
```

### Vercel

Set **Project Settings > General > Node.js Version** to Node `20.x` (preferably the closest available `20.14.x`).

Keeping local and Vercel on the same Node major/minor helps avoid build drift.

## 5) Environment variables setup

Set variables in **Project Settings > Environment Variables**. Configure per environment (`Production`, `Preview`, `Development`) as needed.

### Public variables (`NEXT_PUBLIC_*`)

These are embedded in client bundles. Never store secrets in `NEXT_PUBLIC_*` values.

- `NEXT_PUBLIC_SITE_URL`
  - Production: canonical site URL (example: `https://weeklycryptopulse.com`)
  - Preview: optional preview URL if needed for preview-specific behavior
- `NEXT_PUBLIC_STRIPE_PAYMENT_LINK_SINGLE_ISSUE`
  - Stripe Payment Link URL for **Weekly Crypto Pulse Pro — Single Issue** CTA (safe public URL, not a secret key)
- `NEXT_PUBLIC_STRIPE_PAYMENT_LINK_MONTHLY_BUNDLE`
  - Stripe Payment Link URL for **Weekly Crypto Pulse Pro — Monthly Bundle** CTA (safe public URL, not a secret key)

### Server-only variables (no `NEXT_PUBLIC_` prefix)

No required server-only variables currently.

If introduced later, add them only as non-public variables in Vercel and scope by environment.

## 6) Verify command before deploy

Use the unified check before merging:

```bash
npm run verify
```

`verify` runs:

1. `npm run lint`
2. `npm run typecheck`
3. `npm run build`

## 7) Fresh-environment build validation

Recommended clean check (same approach used by CI-like environments):

```bash
rm -rf node_modules .next
npm ci
npm run verify
```

This confirms the project can install and build from scratch.

## 8) Post-deploy validation checklist

After each Preview/Production deploy, smoke test these routes:

- `/`
- `/reports`
- `/reports/<valid-slug>`
- `/methodology`
- `/disclaimer`
- `/pro`
- `/sitemap.xml`
- `/robots.txt`

Example checks:

```bash
curl -I https://<deployment-url>/
curl -I https://<deployment-url>/reports
curl -I https://<deployment-url>/methodology
```

Expected result: `200 OK` on valid routes.
